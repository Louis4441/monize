# Migrating the MCP server to revision 2026-07-28

Status: **planned**. Nothing here is implemented. The current server speaks the
2025-06-18 / 2025-11-25 shape through `@modelcontextprotocol/sdk` 1.x.

Revision 2026-07-28 is not a set of new features to adopt one at a time. It
removes the two things this server's design rests on -- the session and the
server-initiated request -- so the migration is a redesign of the transport and
of how a write gets confirmed, and it needs its own PR.

## What the revision changes

| Change | What it removes here |
|---|---|
| Sessions and `Mcp-Session-Id` are gone; the protocol is stateless | The whole session table in `mcp-http.controller.ts`, and `resolve(extra.sessionId)`, which is how every tool learns who is calling |
| No `initialize` / `notifications/initialized`; `server/discover` advertises versions, capabilities and identity | The capability handshake `mcp-elicitation-support.ts` reasons about |
| Multi Round-Trip Requests: a result carries `resultType: "input_required"`, and the client retries with `inputResponses` | Server-initiated elicitation, which is how `confirmWrite` asks a human |
| The GET stream and `resources/subscribe` become one `subscriptions/listen` POST-response stream | The GET half of the transport |
| `Mcp-Method` and `Mcp-Name` required on every Streamable HTTP POST | Nothing -- the proxy already recognises both |
| `ttlMs` and `cacheScope` required on `tools/list`, `prompts/list`, `resources/list` | Nothing yet; new fields to emit |
| Tools SHOULD be listed in a deterministic order | Nothing -- pinned by the budget spec |
| `ping`, `logging/setLevel`, `notifications/roots/list_changed` removed; Roots, Sampling and Logging deprecated | The `logging` capability advertised in `createServer` |
| Resource-not-found moves from `-32002` to `-32602` | An error code |
| DCR deprecated in favour of Client ID Metadata Documents; `iss` per RFC 9207 | Part of `oauth/` |
| `inputSchema` / `outputSchema` may use any JSON Schema 2020-12 keyword | Nothing; an option, not an obligation |

The SDK ships as new packages: `@modelcontextprotocol/server` 2.x replaces
`@modelcontextprotocol/sdk` 1.x, with `createMcpHandler` as the HTTP entry point
and Standard Schema in place of the Zod-specific plumbing. One endpoint can
serve both revisions during the transition.

## The two decisions this needs

### 1. What replaces the session, given that identity comes from it

Today `POST /mcp` authenticates a bearer token, stores `{ userId, scopes,
credentialId }` against the session id, and every tool handler calls
`resolve(extra.sessionId)`. `userId` never comes from tool arguments -- that is
the rule the whole server is built on, and INV-MCP-001 binds a session to the
credential that opened it so a narrowed token cannot inherit a wider session's
scopes.

Statelessness does not threaten that: the bearer token is on every request
anyway, so identity can be resolved per request and seeded with
`withUserContext` exactly as the transport already does. What disappears is the
*session* as a thing to bind to. INV-MCP-001 has to be restated as a property of
the request rather than of the session, and its spec rewritten against the new
shape. This is the easy half.

### 2. How a write gets confirmed without a server-initiated request

The hard half. `confirmWrite` (`mcp-context.ts`) asks the human by sending an
elicitation *from the server* and waiting for the answer within
`CONFIRM_TIMEOUT_MS`. Multi Round-Trip Requests invert this: the server returns
`resultType: "input_required"` naming what it needs, and the *client* calls the
tool again with `inputResponses`. Consequences to design for:

- **The tool call is now two calls, and the server holds nothing between them.**
  Everything the second call needs -- which rows, at which amounts, under whose
  authority -- must travel in the interim result and come back, or be stored
  behind an idempotency key the second call quotes. The signed `PendingAiAction`
  the relay path already builds (`AiActionBuilderService`) is the closer model,
  and is probably what both paths should use.
- **`mcp-elicitation-support.ts`'s central lesson survives the rewrite.** Only a
  returned answer is a user's answer; a client that answers for itself is not
  consent. MRTR changes the mechanism, not that rule, and the new code owes the
  same distinction between "declined" and "no dialog reached a human".
- **The relay claim is session-scoped on purpose.** "Does this write belong to
  the web chat" is a question about the calling session, not the user -- with no
  session, that question needs a new answer, and the wrong one routes a direct
  client's confirmation into a browser nobody is watching. Every alternative
  tried before (connection liveness, user-wide, unbounded time) was wrong; do not
  reach for them again because the session is gone.

## Suggested order

1. Emit `ttlMs` / `cacheScope`, drop the `logging` capability, move the
   resource-not-found code. Small, and possible before any SDK change.
2. Add `@modelcontextprotocol/server` 2.x beside the 1.x server and serve both
   revisions from `/mcp`, negotiating on the client's advertised version.
3. Redesign confirmation as MRTR behind the existing `confirmWrite` signature,
   so tool code does not change with the transport.
4. Move identity resolution per request, restate INV-MCP-001, and delete the
   session table once no client negotiates the old revision.
5. Re-answer the relay-claim question, then retire the 1.x server.
